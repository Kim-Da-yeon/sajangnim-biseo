# 정답 라벨 기준서 v7

작성일 2026-11-02. 데이터 목록은 `data/manifest.json`.

## 1. 서비스 범위 (정보 제공)

| 구분 | 내용 |
|---|---|
| 제공 | 공고 원문의 조건 정리, 입력 정보와의 대조, 근거 쪽·문구, 확인 필요 항목, 문의처 |
| 제공 안 함 | 법률 해석·자문, 계약서 검토, 분쟁·권리 판단, 신청서 대리 작성·제출, 선정 예측 |
| 결과 표현 | "공고 조건 일치 / 불일치 / 확인 필요" |
| 금지 표현 | "자격이 있습니다", "선정됩니다", "받을 수 있습니다", "법적으로", "권리가 있습니다" |
| 고정 안내 | 최종 자격은 주관기관이 판단합니다. 법률 문제는 전문가에게 문의하세요. |

`법적으로` 등 금지 표현 검사는 평가 항목에 포함한다. 위 기준만으로 변호사법 위반 위험이 사라진다고 판단하지 않으며, 외부 공개·유료화 전 전문가 검토가 필요하다.

## 2. 데이터 분할

서비스 코퍼스(`data/corpus/corpus.json`)는 소상공인 혜택 공고를 넓게 담으며 라벨이 없다. 점수는 아래 평가셋에서만 산출한다.

| 분할 | 공고 | 쓰임 |
|---|---|---|
| dev | 클린제조 3차, 클린제조 3차 연장, 생활문화, 고용보험료 | 규칙·프롬프트 조정 |
| eval | 브랜드 점프업, 판로개척, 스마트제조, 정책자금 변경 5차(변경 4차 비교), 경영안정 바우처, 보은군 소공인, 재도전성공패키지(추경) | 최종 측정 |

- eval 라벨은 시스템 출력을 보기 전에 작성하고 고정한다.
- 라벨 수정이 필요하면 변경 전후와 사유를 기록한다.
- 판로·스마트·클린은 같은 소공인 사업군이라 문구가 비슷하다. 완전히 독립된 표본으로 보고하지 않는다.
- 공고마다 접수 상태가 다르므로 사례마다 기준일을 지정한다. 고용보험료, 바우처, 보은군은 2026-11-02 기준 공고상 기간 안이다.
- 보은군 공고는 HWPX만 있어 쪽 번호가 없다. 근거는 page=1과 문구로 적는다.

## 3. 조건 라벨 스키마

| 필드 | 값 |
|---|---|
| kind | eligibility / exclusion / period |
| field | 통제 어휘(검증기 `FIELDS`) |
| op | eq, ne, lt, le, gt, ge, in, not_in, between, derived |
| value·unit | 원문 값과 단위 |
| basis | application_date / deadline_date / notice_date / as_of_date / not_stated |
| group | AND / OR:그룹명 |
| applies_to | 조건이 적용되는 유형·자금명, 공통이면 null |
| waives | 이 조건이 충족될 때 면제되는 조건 id 목록, 없으면 [] |
| check | profile / declared / discretionary / unsupported / conflict |
| exception | 판정 구조로 옮기지 못한 예외의 원문, 없으면 null |
| evidence | 쪽, 원문 문구 |

### 작성 규칙

- 모든 술어는 **참이면 통과**로 쓴다. 제외 조건도 같다. 예: 체납 제외는 `tax_arrears eq false`.
- 조건 1개에 판단 1개. "국세·지방세 체납, 채무불이행"은 2개로 나눈다.
- 원문이 기준일을 안 밝히면 추정하지 않고 `not_stated`.
- 표의 제목 기준일과 항목 기준일이 다르면 항목을 따른다. 예: "신청마감일 기준" 표 안의 "신청일 현재".
- 수치 경계를 그대로 보존한다. "10인 미만"은 lt 10, "2억원 미만"은 lt 200000000.
- 본문에 적힌 값은 참조 표시가 있어도 그대로 적는다.
- 값이 붙임·타 문서에만 있으면 그 문서를 근거로 별도 조건을 쓴다. 문서가 없으면 `unsupported`.
- `derived`는 8장에 정의된 개념에만 쓴다.
- 예외가 일부 조건만 면제하면 `waives`로 대상을 지정한다. 전체 자격 면제로 쓰지 않는다.
- 라벨 범위 밖 유형의 조건은 `out_of_scope`에 사유와 함께 적는다.
- 평가자의 재량이 들어가는 문구는 `discretionary`.
- 본문으로 판단할 수 없는 표현은 `unsupported`. 추측해서 구조화하지 않는다.

## 4. 사례 판정 규칙

조건별 상태를 먼저 정하고 공고 단위 상태를 합친다.

| 조건 상태 | 기준 |
|---|---|
| 일치 | 필요한 값이 있고 조건을 만족 |
| 불일치 | 필요한 값이 있고 조건을 위반, 해당 예외 없음 |
| 확인 필요 | 값 없음, 근거 충돌, 예외 해당 여부 불명, unsupported |
| 기관 판단 | discretionary. 합산에서 빼고 카드에 별도 표시 |
| 표기 충돌 | conflict. 값이 위반이면 불일치, 만족하면 확인 필요(같은 공고의 다른 표기로는 위반인 경우) |

| 공고 상태 | 합산 규칙 |
|---|---|
| 불일치 | 불일치 조건이 1개 이상. 다른 값이 비어 있어도 불일치 |
| 확인 필요 | 불일치 없음, 확인 필요 조건이 1개 이상 |
| 일치 | 위 둘 다 아님. 확인 가능한 조건에 한한 결과이며, 기관 판단 항목을 반드시 함께 표시 |

- 자격 상태와 신청기간 상태(접수 전 / 공고상 기간 내 / 마감 / 일정 확인 필요)는 따로 라벨링한다.
- 예산 소진·잠정 종료일이 있으면 "접수 중"으로 단정하지 않고 "공고상 기간 내"로 적고 조기 마감 가능성을 표시한다.
- 한 공고 안의 일정 표기가 다르면 임의로 고르지 않는다. 신청 항목과 공고 기간 등 복수 표기가 일치하면 그 값을 쓰고 불일치를 표시한다. 판단할 수 없으면 일정 확인 필요.
- `declared` 값은 사용자의 입력을 믿고 대조했다는 뜻이다. 사실 검증으로 표현하지 않는다.
- 계산 순서: `applies_to` 적용 → `waives` 적용 → OR 그룹 계산 → 공고 상태 합산.
- 종료일이 공고에 없으면 기간 상태는 "일정 확인 필요"로 둔다.
- "이후"는 기준일 당일을 포함해 해석한다. 참가자 확인 항목이다.
- OR 그룹은 하나라도 일치하면 일치, 모두 위반이면 불일치, 그 외 확인 필요.
- 재량 조항은 공고 대부분에 있어 확인 필요로 합산하면 모든 사례가 확인 필요가 된다. 그래서 합산에서 빼고, 표시 누락을 지표로 잰다.

## 5. 정정 공고 규칙

| 상황 | 기대 동작 |
|---|---|
| 명시적 변경 사항과 대체 관계가 있음 | 해당 항목만 갱신, 근거에 새 공고 표시 |
| 변경 범위가 자격과 무관 | 자격 판정 유지, 변경 사실만 표시 |
| 대체 관계나 범위가 불명확 | 확인 필요 |
| 게시일이 늦다는 사실만 있음 | 정정으로 처리하지 않음 |

실제 쌍 2개를 사용한다.

| 쌍 | 변화 | 기대 |
|---|---|---|
| 클린 3차→연장 (dev) | 마감 10.20→10.30 | 10.25 기준 접수 중, 자격 유지 |
| 정책자금 4차→5차 (eval) | 재난지역 특별지원 금리·한도 문구 추가 | 범위 내 자격 판정 변화 없음 |

## 6. 판정 사례(가상 프로필)

- 프로필은 전부 가상이며 결과에 그렇게 표기한다.
- eval 7개 공고 × 공고당 6개 = 42사례.
- 공고마다 일치 2, 불일치 2, 확인 필요 2를 목표로 한다.
- 사례 유형: 경계값(9명·10명, 2억 전후, 1억 400만원 전후), 제외 코드와 예외, OR 조건, 값 누락, 기준일 차이.
- 3/4/3은 구성 목표이며 정답을 맞추려고 조정하지 않는다.
- 정답은 조건 라벨과 4장 규칙으로만 도출하고, 공고 상태·기간 상태·결정 조건·사유를 함께 동결한다.

## 7. 평가 지표

| 지표 | 정의 |
|---|---|
| 조건 추출 micro-F1 | (kind, field, op, value, unit, basis) 일치. 일대일 매칭, 날짜는 ISO, 금액은 원 단위로 정규화. 기재 시 field·value만 맞은 완화 점수도 별도 표시 |
| 논리 구조 정확도 | group, applies_to, waives, check 일치율. F1과 분리 보고 |
| 공고 상태 일치율 | 원문부터 최종 3상태까지 전체 흐름 |
| 잘못된 일치 수 | 정답이 불일치·확인 필요인데 일치로 낸 건수. 분모와 함께 공개 |
| 확인 필요 재현율 | 정답이 확인 필요인 사례를 확정 판정하지 않은 비율 |
| 근거 적합률 | 문구가 원문에 있고 그 조건을 뒷받침하는 비율. 존재 여부는 자동, 뒷받침은 수동 |
| 기관 판단 표시 재현율 | discretionary 조건을 카드에 표시한 비율 |
| 금지 표현 건수 | 출력 카드에서 1장의 금지 표현 검출 건수 |

비교군은 같은 문서·프로필을 입력한 LLM 직접 응답, 온톨로지 제거판, 단일 에이전트판이다. 모두 같은 출력 형식으로 채점하고 우열을 미리 가정하지 않는다.

## 8. derived 개념 정의

| 개념 | 입력 | 산식 | 근거 |
|---|---|---|---|
| small_merchant(소상공인) | 주업종, 전체 매출액, 상시근로자 수 | 업종별 소기업 매출 기준 충족 AND 업종별 소상공인 근로자 기준 충족 | 공고 참고 표(소상공인기본법 인용) |
| small_craft_business(소공인) | 위 + KSIC 중분류 | small_merchant AND C10~C34 AND 상시근로자 10명 미만 | 공고 참고 표 |
| excluded_industry | KSIC 5자리 | 코드가 제외 목록에 있고 해당 예외가 없으면 제외 | 정책자금 별표1 |
| annualized_revenue | 개업일, 2025년 매출 | 2024년 이전 개업은 신고 매출 그대로, 2025년 개업은 월평균×12. 1개월 미만은 1개월로 계산 | 바우처 공고 |
| revenue_change_rate | 비교 기간의 직전·직전전 매출 | (직전 − 직전전) / 직전전. 기간은 사용자가 선택, 미입력이면 확인 필요 | 정책자금 공고 |

별표의 "코드 중" 표기는 해당 코드의 일부 업종만 제외한다. 세부 업종을 확인할 수 없으면 확인 필요로 둔다.

제외 코드 39개는 브랜드 점프업, 생활문화, 정책자금, 바우처 공고에서 코드 기준 동일함을 확인했다(바우처의 47911은 줄바꿈 표기 차이). 예외 문구의 동일 여부는 라벨 작성 시 대조한다.

소기업 매출 기준은 공고마다 다르다. 예: 음식점업은 생활문화 공고 15억원, 고용보험료 공고 10억원. 출처별로 계산해 결과가 갈리면 확인 필요로 둔다. 어느 쪽이 현행 법령인지는 확인 전이다.

## 9. 한계 (보고서에 그대로 기재)

- 라벨은 참가자 1인이 작성했고 전문가 검증은 받지 않았다.
- 프로필은 가상이므로 현장 사용 효과를 측정한 결과가 아니다.
- 평가는 중기부 공고와 지자체 연계 공고 1건에 한정되며, 지자체 공고 전반으로 일반화하지 않는다.
